Introduction

Dans le cadre de notre projet intégrateur visant à concevoir une plateforme d'interconnexion et de mentorat au sein de notre établissement (IFRI), le système a été découpé en plusieurs modules indépendants confiés aux différents membres de l'équipe de développement.

Ce rapport présente le travail réalisé sur le Module 4, responsable de la logique métier la plus critique de l'application : l’algorithme de Matching. L'objectif principal de ce module est de mettre en relation de manière automatisée, fluide et cohérente les profils d'apprenants (demandeurs de compétences) et de mentors (offreurs de compétences) en exploitant les informations stockées dans la base de données.

Les technologies retenues pour concevoir ce module sont le langage Python, le framework Flask pour l'exposition de l'API, l'extension Flask-CORS pour la sécurité des échanges, et SQL (MySQL) pour la persistance des données.

I. Architecture et Structuration du Module

Afin de respecter les directives de centralisation de l'équipe et de garantir une intégration propre sur notre dépôt commun GitHub, l'arborescence du module a été restructurée de manière stricte.

Mon espace de travail est entièrement isolé et se compose ainsi :

  • backend_membre4_matching/ : Le dossier racine officiel de mon module.
    • app_M4.py : Le point d'entrée principal de l'application Flask. Il initialise le serveur, configure les règles de sécurité CORS et enregistre les Blueprints.
    • TP_MATCHING.sql : Le script de structure et d'insertion utilisé pour l'environnement de test local.
    • matching/ : Un sous-dossier contenant le cœur de l'algorithme.
      • matching.py : Le script Python contenant les routes de l'API et les requêtes logiques de l'algorithme de correspondance.
      • README_Matching.md : La documentation technique interne destinée à mes camarades pour faciliter l'interconnexion de nos modules.

Cette organisation logicielle permet de séparer le lancement de l'application (la configuration du serveur web) de la logique mathématique et algorithmique du matching.

II. Base de Données et Jeu de Tests

II.i. Rôle du fichier SQL

Pour s'assurer de la pertinence des résultats de l'algorithme avant toute mise en réseau, une phase de modélisation et d'injection de données a été menée. Le fichier TP_MATCHING.sql a été conçu spécifiquement dans ce but. Il contient un jeu de données fictives complet simulant une activité réelle sur la plateforme : l'insertion de plusieurs profils de mentors, d'apprenants, de filières universitaires et de compétences distinctes. L'algorithme de matching s'appuie sur des requêtes SQL exploitant des jointures relationnelles complexes (JOIN utilisateurs, JOIN competences).

II.ii. Logique de Calcul des Scores et Classement des Profils

Pour que le matching ne soit pas une simple liste brute, j'ai mis en place un système de calcul de score de pertinence cumulatif sur un total de 100 points maximum pour chaque mentor trouvé, permettant de classer les résultats du meilleur au moins bon :

  • Le Format du Mentorat (Score de base - Max 50 points) : Si le mentor propose un format en PRESENTIEL, il obtient un bonus complet de +50 points. S'il propose un format EN LIGNE, le bonus est de +40 points.
  • Le Score de Filière (Poids stratégique - Max 20 points) : L'algorithme vérifie si l'apprenant et le mentor appartiennent à la même filière d'étude. Si les filières correspondent exactement, un bonus de +20 points est attribué au score global. Cela garantit la cohérence du parcours académique.
  • Le Score de Compétences (Score Exact - Max 30 points) : Le système compare la liste des compétences recherchées par l'apprenant avec celles proposées par le mentor. Chaque correspondance exacte (exact match) sur une compétence technique ajoute des points supplémentaires au score global.

Mécanisme de classement : Une fois les scores individuels calculés pour chaque profil, l'algorithme effectue un tri décroissant. Les mentors ayant le score le plus élevé sont positionnés en tête de liste dans la réponse JSON renvoyée au frontend, offrant ainsi une expérience de recherche optimisée pour l'utilisateur.

III. Tests en Réseau et Validation Multi-Machines

C'est la phase majeure de validation du projet. Pour prouver que le module est prêt pour un déploiement de production et qu'il peut communiquer avec les modules des autres membres (le frontend ou l'authentification), le serveur a été extrait de l'environnement isolé localhost pour être ouvert sur le réseau local.

III.i. Configuration Réseau et URLs de Validation

Le script Flask a été configuré pour écouter sur l'ensemble des interfaces réseau disponibles. Lors de la phase de test, la machine hébergeant le code s'est vu attribuer les paramètres réels suivants :

  • Adresse IP locale du serveur Backend : 192.168.1.103
  • Port d'écoute du serveur : 5000
  • URL principale d'accès à l'API : http://192.168.1.103:5000/

Points de terminaison (Endpoints) de l'API validés en réseau :

  1. Route d'index (GET http://192.168.1.103:5000/) : Utilisée pour vérifier le statut du serveur à distance. Elle renvoie un code de statut HTTP 200 OK confirmant que le serveur Flask est fonctionnel.
  2. Route du Matching (GET http://192.168.1.103:5000/matching?user_id=1) : C'est le point d'accès réseau à l'algorithme. Lorsqu'elle est appelée depuis une machine distante, elle exécute la logique de mise en relation et retourne un flux de données structuré au format JSON.

III.ii. Matériel et Logiciels Utilisés

La validation de cette architecture distribuée a nécessité la mise en place d'un véritable laboratoire de test impliquant plusieurs ordinateurs connectés sur le même sous-réseau et l'utilisation de la suite logicielle suivante :

  • PyCharm (IDE) : L'environnement de développement utilisé pour coder, debugger et exécuter le serveur Flask en mode d'écoute global (0.0.0.0).
  • Serveur de développement Flask : Configuré avec le débuggeur actif, il a servi de serveur applicatif web pour traiter les requêtes en temps réel.
  • Navigateur Web (Google Chrome) : Utilisé sur les machines clientes du réseau local pour formuler les requêtes vers l'adresse du serveur et inspecter les réponses JSON.
  • Terminal Windows & Git : Mobilisés pour analyser la configuration réseau (ipconfig) et gérer le suivi de version.

III.iii. Gestion de la Sécurité CORS

L'un des défis majeurs des tests multi-machines est le blocage de sécurité des navigateurs lié au mécanisme de partage de ressources entre origines multiples. L'intégration du module Flask-CORS avec une configuration d'ouverture globale ({"origins": "*"}) a été indispensable pour autoriser explicitement les navigateurs des ordinateurs clients à consommer les données sans restriction de sécurité.

IV. Difficultés Rencontrées et Solutions Apportées

Le développement de ce module en équipe a présenté des défis d'ingénierie logicielle qui ont été résolus de manière autonome :

  1. Conflits de fichiers et de structures sur Git : Des dossiers de configuration propres à l'environnement local (.idea) avaient été envoyés par erreur sur le dépôt GitHub distant.
    • Solution : Utilisation de la commande git rm -r --cached .idea pour retirer ces configurations en ligne sans les effacer de la machine locale.
  2. Résolution des chemins d'importation Python : L'ouverture du projet global d'équipe sous PyCharm provoquait des erreurs de détection des sous-dossiers lors des imports.
    • Solution : Alignement rigoureux des imports absolus (from backend_membre4_matching.matching.matching import ...) pour assurer une compatibilité parfaite.

Conclusion

Le travail effectué sur le Module 4 a permis de livrer un algorithme de matching pleinement opérationnel, performant et conforme aux exigences du cahier des charges. L'implémentation de tests en réseau local réels à l'aide de plusieurs ordinateurs démontre la viabilité technique de l'API et sa capacité à s'intégrer de façon transparente avec l'interface utilisateur frontend.

L'environnement de développement est désormais propre, documenté, et entièrement disponible sur le dépôt GitHub de l'équipe pour les phases finales du projet intégrateur.
